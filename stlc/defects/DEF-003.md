# DEF-003: GET /messages returns `name: null` and `email: null`, but the contract says string

## Summary

An authenticated user sends a message without `name` or `email`, which the contract allows
(`ContactRequest` requires only `subject` and `message`, and `email` is required only when not
authenticated). `GET /messages` then lists the message with `"name": null, "email": null`. Both
`ContactResponse` and `ContactResponseAuthenticated` type these fields as non-nullable `string`, so
the list response breaks the contract.

## Steps to reproduce

1. Register and log in a fresh user; use its bearer token.
2. `POST /messages` with `{"subject":"customer-service","message":"QA <marker> automated test message for the account list. Please ignore."}`. The response is 200.
3. `GET /messages` with the same token.

## Expected

AC-10 (API, TC-028): `GET /messages` returns 200 and matches the contract's
`PaginatedContactMessageResponse`, whose items have `name` and `email` of type `string`.

## Actual

200 with
`{"data":[{"id":"01m59avp220eg8c6p92bfm474w","user_id":"01m59avmz1e7v2wgcsdpmvnxyq","name":null,"email":null,"subject":"customer-service","message":"…","status":"NEW","created_at":"2026-10-19 05:41:27"}],…}`.
The contract matcher reports that `/data/0/name` and `/data/0/email` must be strings. The listing
itself is correct (subject, status and `created_at` are right). Same on retry. Either the API
should fill in the user's name and email or omit the fields, or the contract should mark them
`nullable`.
