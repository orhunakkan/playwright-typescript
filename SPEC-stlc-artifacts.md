# Spec: stlc-artifacts

Module id: `stlc-artifacts` · Parent: [SPEC.md](SPEC.md) · Depends on: `foundation` · Status: **complete 2026-10-19**

## Objective

Define the files each STLC phase produces, in a format that is:

1. readable and reviewable by a human in a PR, and
2. strict enough that **scripts**, not agents, can check gates, compute coverage, and build the
   traceability matrix.

The agents (next module) fill in these templates, and the scripts here judge the result.

## ID scheme and tags

| ID              | Scope                   | Example              | Where it is defined                              |
| --------------- | ----------------------- | -------------------- | ------------------------------------------------ |
| feature slug    | global, kebab-case      | `product-search`     | folder name `stlc/<feature>/`                    |
| `REQ-<feature>` | one per feature         | `REQ-product-search` | `01-requirements.md` front matter                |
| `AC-<n>`        | unique within a feature | `AC-3`               | `01-requirements.md` heading `### AC-3: <title>` |
| `TC-<nnn>`      | unique within a feature | `TC-012`             | `03-test-cases.md` table row                     |
| `DEF-<nnn>`     | global, sequential      | `DEF-007`            | file `stlc/defects/DEF-007.md`                   |

- **Test tags:** `{ tag: ['@REQ-<feature>', '@AC-<n>', '@TC-<nnn>'] }`. Every test generated for
  a feature carries all three. An AC is identified by the pair `(REQ, AC)`, so `@AC-1` can appear
  in different features without colliding.
  - Filter: `npx playwright test --grep "@REQ-product-search.*@AC-2"`. Probed: this matches with
    tags on the test, or with `@REQ` on the `describe` and `@AC` on the test, and excludes other
    features' `@AC-2`. Keep the REQ → AC → TC order.
  - Probed: the JSON report stores tags **without** `@`, per spec (`["REQ-probe","AC-1","TC-001"]`).
- **Known defect:** `annotation: { type: 'issue', description: 'DEF-<nnn>' }`. The test stays
  failing. Probed: annotations appear per test in `reports/results.json`.
- **`@flaky`:** marks a quarantined test. It also needs an `issue` annotation pointing at a DEF.
  A `@flaky` test without one fails the lint check.

## Artifacts per feature: `stlc/<feature>/`

Each file starts with flat `key: value` front matter, parsed with a small regex and no YAML
dependency:

```
---
feature: product-search
phase: 2-test-plan
status: draft            # draft | approved | complete
updated: 2026-10-19
---
```

| File                 | Phase | Strict, machine-read parts                                                                                                                                           | Free-form parts                                                                  |
| -------------------- | ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `01-requirements.md` | 1     | `source: provided \| inferred`; one `### AC-<n>: <title>` heading per AC, each followed by a `risk: high \| medium \| low` line                                      | user stories, ambiguities, assumptions, questions                                |
| `02-test-plan.md`    | 2     | **Coverage matrix** table: `\| AC \| e2e \| api \| a11y \| perf \| visual \|` with `x` or blank; **Exit criteria** list                                              | scope, out of scope, environments, risks, schedule                               |
| `03-test-cases.md`   | 3     | Table `\| TC \| AC \| type \| title \| priority \|`, where title starts with `positive:`, `negative:` or `boundary:`                                                 | steps and expectations per TC; links to `specs/*.md` from the Playwright planner |
| `04-execution.md`    | 6–7   | Run block generated by script (counts, failed tests); **Triage** table `\| test \| verdict \| DEF \| note \|` with verdict `product \| test \| environment \| flaky` | triager's reasoning per failure                                                  |
| `05-closure.md`      | 8     | Traceability matrix and exit-criteria result, both **generated between markers** `<!-- generated:start -->` … `<!-- generated:end -->`                               | summary, lessons, recommendations                                                |

**Gate rule:** phase _n_ may start only when every artifact before it has `status: approved` or
`complete`. `02-test-plan.md` needs a human to set `approved`. No script or agent ever sets it.

## Defects: `stlc/defects/DEF-<nnn>.md`

- Front matter: `id`, `feature`, `ac`, `severity` (`critical | major | minor | trivial`),
  `status` (`open | fixed | wont-fix | duplicate`), `found` (date), `env` (the `ENV` name and
  `BASE_URL`), `test` (`file:line`).
- Body sections: Summary · Steps to reproduce · Expected · Actual · Evidence (trace or screenshot
  path from `test-results/`).

## Templates: `stlc/_templates/`

One template per file above, plus `DEF.md`. Each holds the strict skeleton and short guidance
comments. Agents copy them and never invent structure.

## Scripts (deterministic, no LLM)

All live in `scripts/stlc/`, run with `node`, and share one parser in `scripts/stlc/artifacts.ts`.

| Command                                        | Does                                                                                                                                                        | Exit code                                |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `npm run stlc:lint -- <feature>`               | Checks artifact structure: front matter, ID formats and uniqueness, every TC's AC exists, every planned AC×type has at least one TC, defect files are valid | 1 on any violation                       |
| `npm run stlc:gate -- <feature> <phase>`       | Checks that the artifacts before `<phase>` are approved or complete                                                                                         | 1 if the gate is closed, with the reason |
| `npm run stlc:new -- <feature> [phase]`        | Creates `stlc/<feature>/01-requirements.md`, or one later artifact when its phase starts (as built: lazy, see below)                                        | 1 if the folder already exists           |
| `npm run stlc:defect -- <feature> <AC> <test>` | Creates the next `DEF-<nnn>.md` from the template                                                                                                           | 0                                        |
| `npm run stlc:run-summary -- <feature>`        | Reads `reports/results.json` and writes the generated run block in `04-execution.md`                                                                        | 0                                        |
| `npm run stlc:trace -- <feature>`              | Joins 01 + 02 + 03 + results + defects into the matrix below and writes it into `05-closure.md`                                                             | 1 if exit criteria fail                  |

Traceability matrix, one row per TC:

```
| AC   | TC     | type | test (file:line)                | chromium | firefox | … | defect  |
| AC-2 | TC-004 | e2e  | tests/e2e/product-search/…:12   | pass     | pass    | … |         |
| AC-3 | TC-007 | api  | tests/api/product-search/…:8    | fail     | —       | … | DEF-002 |
| AC-4 | —      | —    | —                               | —        | —       | … |         | ← uncovered AC
```

It also reports:

- AC coverage %
- untagged or orphan tests (they have a `@REQ-<feature>` tag but an unknown TC)
- the flaky rate

It then evaluates the exit criteria from `02-test-plan.md`. Defaults: 100% AC covered by a
passing test or an open defect; no open `critical` defect; flaky rate below 2%.

## Testing the scripts

- `node --test scripts/stlc/` covers the parser, the gate logic and traceability, using fixture
  artifacts and a fixture `results.json` in `scripts/stlc/__fixtures__/`.
- `npm run test:scripts` runs these. They are part of the pre-commit gate for this module.
- No Playwright and no network involved.

## Changes to SPEC.md

- The phase table gets `04-execution.md` (phases 6–7). The old draft jumped from 03 to 05.
- The code-style example's tags already follow `@REQ-<feature>` / `@AC-<n>` / `@TC-<nnn>`.

## Tasks

1. **Parser and lint:** `artifacts.ts`, `stlc:lint`, templates, fixtures, unit tests.
   _Verify:_ `npm run test:scripts` is green, and a fixture with a duplicate AC fails lint.
2. **Gate and new:** `stlc:gate` and `stlc:new`. _Verify:_ unit tests; `stlc:new demo` passes lint
   (then deleted).
3. **Defects and run summary:** `stlc:defect` and `stlc:run-summary`. _Verify:_ unit tests against
   the fixture `results.json`.
4. **Traceability and exit criteria:** `stlc:trace`. _Verify:_ unit tests cover uncovered AC,
   orphan test, open critical defect, flaky over threshold, and the all-green case.

Each task: lint, format, typecheck and `test:scripts` green, then one commit.

## Success criteria

- [x] Every gate, coverage and exit-criteria decision can be reproduced from files by running
      one command.
- [x] `05-closure.md`'s matrix is regenerated byte-identically from the same inputs. This is
      unit-tested, including surviving `npm run format`.
- [x] No new runtime dependencies. Parsing uses regex on the strict formats.
- [x] Unit tests cover every exit-code path in the table above. That's 58 `node:test` tests on the
      logic, plus a CLI smoke run of all six commands covering exit codes 0, 1 and 2.

## As built (2026-10-19)

Where the build differs from the plan above, this section is what's true.

- **Front-matter `phase` values:** `requirements`, `test-plan`, `test-cases`, `execution`,
  `closure`. These replace the planned `2-test-plan` style.
- **`REQ-<feature>` is derived from the folder name.** It isn't stored in front matter.
- **Placeholders** use `{{…}}`.
  - Lint allows them only in `draft` artifacts.
  - HTML comments are blanked before parsing, so guidance text is never read as content.
  - `stlc/_templates/` is excluded from Prettier, which would otherwise rewrite front-matter
    `{{x}}` as a YAML map.
- **Allowed values:** `priority` is `high | medium | low`. Exit-criteria keys are
  `ac-coverage-min`, `open-critical-max` and `flaky-rate-max`, compared with ≥ / ≤.
- **AC status:**
  - `covered`: at least one of its tests ran, and every failing test is linked to an **open**
    defect.
  - `failing, untriaged`: something failed with no open defect linked.
  - `not run`: none of its tests ran.
  - A failing test links to a defect through any of three routes: a triage row in `04`, the
    defect's own `test` field, or a `DEF-nnn` `issue` annotation.
  - Flaky rate is flaky tests divided by executed (non-skipped) tests of the feature.
- **Gates:** every gate is also closed while `stlc:lint` reports issues. Phase 7 needs `04` to
  exist, and phase 8 needs `04` approved or complete.
- **Generated blocks** are fenced with `<!-- prettier-ignore-start/end -->`.
- **Run metadata:** `playwright.config.ts` records `env`, `baseUrl` and `apiUrl` in `metadata`, so
  reports and defects name the environment that actually ran.
- **Not enforced by scripts:** that only a human sets `02-test-plan.md` to `approved`. Enforcing it
  (for example with a hook that blocks agent edits to that line) belongs to `stlc-agents`.
- **Harness findings F1–F8** (SPEC-test-harness.md) are not DEFs yet. A DEF needs a feature and
  an AC, and the `@example` tests are not a feature. They get converted in `pilot`, when the
  product-search feature owns those behaviours.

## Out of scope

- Writing the content of artifacts (`stlc-agents`).
- Syncing to Jira or ADO (not in the MVP).
